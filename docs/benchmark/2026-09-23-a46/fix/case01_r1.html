得意なデータ
関係が固定的で、結合して集計したい正規化済みの業務データ。
寿命が短く単純な値。セッションやカウンタ、一時的なキャッシュ。
項目が案件ごとに揺れる半構造データ。入れ子の JSON をそのまま持てる。
トランザクション
複数テーブルにまたがる ACID を標準で持つ。会計処理でも安心して使える。
MULTI で原子実行はできるが、ロールバックのない単純な一括実行に近い。
単一文書は原子的。複数文書のトランザクションは使えるが代償が大きい。
スケール
まず垂直に伸ばす。読み取りはレプリカ、書き込みは分割の設計が必要。
Cluster で水平に伸びる。メモリ量が上限なので容量設計が効いてくる。
シャーディング前提の設計。キー選びを誤ると偏って効果が出ない。
運用の手間
知見も道具も揃っている。VACUUM と長時間トランザクションだけ要注意。
運用は軽いが、永続化とフェイルオーバーの設定は事前に詰めておきたい。
スキーマ変更は楽な反面、実質の形はアプリ側の規律に依存してしまう。
うちでの用途
注文・請求・ユーザーなど、整合性が売上に直結する中核データを置く。
ログイン情報と API のレート制限、重い集計結果の一時保存に使う。
審査ログや外部 API の生レスポンスなど、形の定まらない記録の置き場。
※ 評価は当チームの現行ワークロード（1 日あたり書き込み 300 万件規模）を前提とした相対比較です。
