データストア比較（技術選定資料・2026 年度）

項目
RDB（PostgreSQL）
KVS（Redis）
ドキュメント DB（MongoDB）
得意なデータ
正規化した業務データ。型と制約をスキーマ側で守りたいものに向く。
短命で小さい値。セッションや順位表など、捨ててよい状態の置き場。
形のそろわない文書。案件ごとに項目が増えるデータを丸ごと持てる。
トランザクション
複数テーブルにまたがる ACID を標準で持ち、整合性の担保が楽。
単一コマンドは原子的だが、複数キーをまたぐ整合は保証されない。
単一文書は原子的。複数文書にまたがる更新は制約つきで使える。
スケール
まず垂直に伸ばす。読み取りはレプリカへ逃がすのが定石になる。
クラスタで水平に伸びる。分割の良否はキーの設計で決まる。
シャーディングで水平に伸びるが、キー選定を誤ると偏りが出る。
運用の手間
バックアップと版上げの手順が確立していて、事故の予測が立つ。
単体は軽いが、クラスタの運用と容量の見張りに手が要る。
スキーマ変更は楽な反面、索引とシャードの設計に手間がかかる。
うちでの用途
注文・課金など、整合性が必要な中核データの置き場として採用。
セッション、レート制限、ジョブの待ち行列に限って使う。
監査ログと外部 API の生の応答を、加工せず貯める用途に使う。
