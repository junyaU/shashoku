データストアの比較（技術選定資料）
3 つの選択肢を 5 項目で比較する。用途欄は当プロダクトでの想定。
項目
PostgreSQL（RDB）
Redis（KVS）
MongoDB（ドキュメント DB）
得意なデータ
関係が明確で整合性の要る業務データ。正規化した表で持つ形に向く。
短命で小さい値。セッションやカウンタなど、取り出しが速ければよいもの。
形の揃わない文書データ。項目が増減する設定やログを丸ごと入れられる。
トランザクション
複数の表にまたがる ACID を標準で持つ。金額を扱う処理はここへ寄せたい。
MULTI/EXEC で一括実行はできるが巻き戻しはない。整合性は呼ぶ側の責任。
単一の文書は原子的。複数文書にまたがる更新は使えるが代償が大きい。
スケール
読みはレプリカで伸ばせる。書き込みの分割は自前の設計が必要になる。
クラスタで水平に伸ばせる。ただし全データがメモリに載る前提になる。
シャーディング前提の設計。シャードキーの選び方で性能が大きく振れる。
運用の手間
バックアップと版上げの手順が枯れている。監視すべき指標も情報が多い。
設定は単純だがメモリ枯渇が即障害になる。追い出し方針を先に決める。
索引設計とスキーマの揺れの管理が要る。版上げの影響範囲が読みにくい。
うちでの用途
注文と請求の正データ。集計バッチの参照先も当面はここに置く方針。
API のレート制限とセッション。ジョブの待ち行列も当面は兼ねさせる。
外部連携の生ログ置き場。項目が変わりやすい取り込み前データに使う。
