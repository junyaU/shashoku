得意なデータ
正規化された関係データ。型と制約を効かせたい業務データに向く。
単純なキーと値。セッションやカウンタなど短命で高頻度のもの。
入れ子の多い半構造データ。スキーマが固まらない段階に向く。
トランザクション
複数テーブルにまたがる ACID を標準で持ち、分離レベルも選べる。
MULTI/EXEC はあるがロールバックがなく、保証は限定的である。
4.0 以降は複数文書のトランザクションが使えるが代償は大きい。
スケール
まず垂直に伸ばす。読み取りはレプリカ、書き込みは分割が要る。
Cluster で水平に伸びる。メモリ量がそのまま容量の上限になる。
シャーディングが前提の設計。シャードキーの選定で決まる。
運用の手間
バキュームと統計情報の管理が要る。知見は社内に溜まっている。
運用は軽いが、永続化と切り替えの設計を誤るとデータを失う。
監視項目が多い。版による挙動の違いに注意が要る点が悩ましい。
うちでの用途
注文と請求の中心データ。整合性を最優先する領域で使っている。
API のレート制限とセッション、重い集計結果の短期キャッシュ。
監査ログと外部連携の生データ置き場。検索は別系統に任せる。
