# 検証結果: 「AI が生成した HTML は、ブラウザなしで日本語の品質を保って PNG になるか」（2026-09-23）

対象: shashoku main c157766（release ビルド、既定フォント埋め込み）。比較: Satori 0.33.5 + @resvg/resvg-js 2.6.2（Node 20.18.1）。
機械: i9-14900KF / WSL2 Ubuntu 22.04。すべての成果物はこのディレクトリ（`exp/`）。数値は `results.json` から再集計した。

## 0. 実験の設計

依頼 10 件（`requests.md`。資料・wiki・SNS 向け 5 件 + サーバーが自動生成する 5 件。製品に合わせて選んでいない）を、次の 4 通りで PNG にした。
生成はすべて opus のエージェント。人の作業時間は測っていない（反復回数 = CLI 実行回数で代用）。

| 経路 | 生成者に渡した情報 | 出口 | ディレクトリ |
|---|---|---|---|
| A→C | 何も渡さない（普段どおりの完全な HTML 文書） → 別のエージェントが README の対応範囲を見ながら**エラーが名指ししたものだけ**を直す | shashoku CLI | `a_plain/` `c_fix/` |
| B | README の対応範囲の抜粋 111 行（`skill_shashoku.md`）だけ | shashoku CLI | `b_guided/` |
| D | Satori の README だけ | satori-html → satori → resvg | `satori/` |
| D-plain | A の完全な HTML をそのまま。通らなければ機械的な前処理を 3 段まで | satori | `satori/plain/` |

参照: A の HTML を Windows 側の headless Chrome で撮った画像（`a_plain/chrome/`）。fidelity（1〜5）はエージェントの自己評価で、B・C・D の代表例（各 5〜10 枚）はオーケストレーターが目視で確かめた。

|---|---|---|---|---|---|
| **B: 対応範囲を渡した AI → shashoku** | **10/10** | **10/10**（エラー 0、警告 0） | 1 | **4.7** | なし（table→flex、ul→flex、矢印→「→」の代替 3 件） |

| D: Satori の README を渡した AI → Satori | 10/10 | **1/10**（exit 0 は 10/10） | 2（1〜3） | 4.1 | ルビ・縦書き・「高さは内容に合わせて」を諦めた |

## 2. 普段の AI の HTML は何で止まるか（A の 10 件の静的解析 + C の 180 件のブロッカー）

タグ: 外枠（html/head/body/meta/title/link）10/10、li 2、table 1、ol/ul/strong/code/header/footer 各 1。Google Fonts の `<link>` 10/10。絵文字 4/10。

| 対応外のプロパティ | 使った件数（/10） | C で失われた見た目 |
|---|---|---|
| `box-sizing` | **10** | なし（幅を引き算すれば同じ。hint で直せた） |
| `background` の gradient 値 | **10** | 背景・バッジ・文字のグラデーション（単色に） |
| 擬似要素 `::before/::after`（`content`） | **8** | 矢印の頭・引用符・箇条書きの点・帯 |
| 子孫結合子セレクタ | 8 | なし（クラスに書き換え） |
| `border-top`（辺ごとの罫） | **8**（bottom 4、left 3、right 1） | **表の罫・段の区切り・見出し下のアクセント**（代替なし） |
| `overflow` | 7 | 角丸のクリップ |
| `position`（+ top/left/z-index/inset） | 7 | 注記の位置合わせ・光の飾り。実要素に置くと箱が流れの中に落ちる（case07 の茶色い箱、case09 の青い四角） |
| `box-shadow` | 6 | 影 |
| `min-height` / `max-width` | 5 / 1 | なし（固定値に） |
| `opacity` `transform` `text-shadow` `background-clip` | 3 / 2 / 1 / 1 | `background-clip:text` を消すと `color:transparent` が残り**文字が消える** |
| `grid-template-columns` / `align-self` / `list-style` | 1 / 1 / 2 | grid→flex で 3 等分が崩れる |
| `flex-wrap` / JPEG | **0 / 0** | — |

C の 180 件の内訳: property 112（62%）/ selector 20 / value 20 / tag 13 / wrapper 10 / unit 4 / image 1。
**170/180 は読めば直し方が決まるが、エラーが 1 回に 1 件しか出ないので 190 回の CLI 実行になった。**

## 3. 対応範囲を渡した AI（B）で足りなかった情報

`skill_shashoku.md`（README 抜粋）で効いたのは box-sizing の注記と計算例、縦書きの 3 点、単位の一覧。足りなかったのは「使えるもので普通の表・箇条書き・タグ・縦中央揃え・注記の位置合わせをどう作るか」の最小例と、
`line-height` の単位なし数値の可否、`margin` の 4 値指定の可否、セレクタの結合の範囲、縦書きでの margin/padding の向き、ルビを付けた行の行送りの目安。CLI は成功時に何も出さず、`--height` 省略時の実際の高さが分からない。

## 4. 日本語の見え方（同じ依頼を両者で。オーケストレーターが目視）

| 観点 | shashoku | Satori |
|---|---|---|
| 行頭の句読点・閉じ括弧、行末の開き括弧、小書きかな | 10 件で 0 か所 | **10 件で 0 か所。UAX #14 の `linebreak` を使っており基本の禁則はある**（DESIGN.md §1 の「禁則処理がない」は現在の Satori には当てはまらない） |
| 両端揃え（`text-align: justify`） | 効く（case05） | 無い。行末が 0〜1 字ぶん不揃い |
| 約物の詰め（「（木）」「。句読点は、」） | 詰まる | 詰まらず全角の空きが残る |
| 和欧文間のアキ | 入る | 入らない（AI が半角空白を打って回避） |
| ルビ | 正しい（case03/07。欧文の親文字にも） | **無視され「高橋 遥たかはし はるか」と連結**（exit 0）。代替は別行 |
| 縦書き | 正しい（case10） | **無視され横書き**（exit 0）。代替は 1 文字 1 div の擬似縦書き。折り返し・禁則なし |
| 高さを内容に合わせる | `--height` 省略で追従（case01〜04, 08, 09） | 必須。6 件で目視調整（余白 55〜175px か下端の切れ） |

## 5. 導入と実行コスト

> **読み方の注意（2026-09-23 追記）**: 下の cold の比較で出た「起動 10 倍・メモリ 1/4」は、**1 枚ごとにプロセスを起動する条件**での差で、主因は日本語特化ではなく「C++ のネイティブ実行ファイルが必要な処理だけを動かす」こと（Node / V8 の起動、モジュール読み込み、wasm 初期化、JS でのフォント解析を省く）と、SVG を経由しない描画経路にある。**常駐したサーバー内で連続生成する条件では差が縮む**可能性が高く（Satori の warm は 1 枚 15.7 ms）、常駐・同時生成の比較は別に測る。「ランタイム不要」は「利用者が Node などの言語ランタイムを別途入れなくてよい」の意味で、glibc への動的依存は残る（README「ビルド」の配布方針）。

| | shashoku（release CLI） | Satori + resvg（Node 20） |
|---|---|---|
| 導入 | 単一バイナリ 12.5 MB（既定フォント 9 MB 込み）。追加なし | Node ≥ 16（この機械は v12 で不可。公式バイナリ 25.8 MB を展開）+ npm 27 パッケージ 20 MB、ネイティブ addon。**合計 116 MB** |
| cold（1 枚、プロセス起動込み） | **10〜30 ms**（中央値 20）/ RSS 37〜47 MB | **0.18〜0.24 s** / RSS 177〜208 MB |
| 常駐（初期化後の 1 枚。10 ケースの中央値の中央値。2026-09-23 夜に追加測定 `perf2/REPORT.md`） | **16.8 ms**、RSS 29 MB / VmHWM 33 MB。同じケースを 1000 枚連続で描いても RSS は 1 バイトも動かない | **15.4 ms**（`setImmediate` で譲る時間の外。内なら 15.6）、RSS 283 MB。ケース別では shashoku が速い 4 件・Satori が速い 6 件。**1 枚あたりの優劣は言えない**（5 件は寸法が違い、PNG の圧縮の強さも揃えられない） |
| 同時生成（処理量 枚/秒、VmHWM。N ごとに別プロセスで 3 回の中央値） | 1 本 57（45 MB）/ 4 本 221（95 MB）/ 8 本 369（162 MB）/ **16 本 558（295 MB）**。`LoadedFonts` / `LoadedImages` を全スレッドで共有。1 本増やすと 16.6 MB | 1 プロセス `Promise.all`: 1 本 55 → 16 本 **59**（246 → 431 MB。JS は単一スレッドなので処理量が増えない）。`worker_threads`: 1 本 55 → 16 本 **395**（271 MB → **2.6 GB**。フォント・wasm・V8 ヒープを共有できず 1 本 156 MB） |
| 連続生成のメモリ | 純粋関数。実行をまたぐ状態なし | 1 リクエスト 1 枚のようにイベントループが回る使い方なら**頭打ち**（2000 枚で 218 MB）。譲らない密なループでは resvg の pixmap の解放が先送りされ **4.7 MB/枚で線形に増える**（`global.gc()` では戻らない。1000 枚で 4.9 GB）。リークではなく解放の先送り（2026-09-23 夜の調査 `satori/memory/REPORT.md`。前回書いた「50 枚後 448 MB が戻らない」は密なループでの観測） |
| 壊れた入力 | エラー（exit ≠ 0、位置つき） | `<table>` の SVG で resvg が Rust panic → **SIGABRT（exit 134）**。`<img width="56">` は警告のうえ画像なしで exit 0 |

## 6. 注意（この実験で言えないこと）

- N = 10、生成者は 1 モデル（opus）。「普段の AI」の HTML は Claude の癖を反映する（他のモデルは grid や `<table>` をもっと使うかもしれない）
- A の生成エージェントは同じリポジトリの文脈（CLAUDE.md）を持っていたため「制限を考慮しない」と明示したが、完全な隔離ではない。結果（box-sizing 10/10、擬似要素 8/10、外枠 10/10）は制限を意識した形跡がないので影響は小さいと見ている
- 人の修正時間は測っていない。反復回数は「エラー 1 件 = 1 回」の定義
- サーバー安全性（巨大入力・時間・同時実行時のメモリ）は別枠。未検証
