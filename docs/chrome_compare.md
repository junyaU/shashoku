# Chrome（headless）との比較と、差の分類

[scripts/compare/](../scripts/compare/) の使い方は [scripts/compare/README.md](../scripts/compare/README.md)。
この文書は **何を比べているか** と **出た差をどう読むか**、そして **いま出ている差の一覧**。

単体テストとゴールデンが保証しているのは「以前と同じ絵が出る」ことで、「組版として正しい絵が
出る」ことではない。過去に、テストが全部通ったまま絵が間違っていた事故が 2 回ある
（縦書きのルビが左右逆 / `font-weight: 700` なのに Regular）。#15 の比較はその穴を塞ぐための
観測手段で、**Chrome に近づけるためのものではない**。狙いは「機能同士の組み合わせで
情報や意味が落ちるのを見つける」こと。

---

## 1. 何を比べるか

ピクセル一致は目標ではない（DESIGN.md §4）。判定は 4 つだけ。

| 判定 | shashoku | Chrome |
|---|---|---|
| **改行位置** | `--dump-stage box` の各行の `fragments[].text` を `inline_start` 順に連結。**`rt` の断片は `baseline < 行の baseline` で先に落としてから並べ替える** | クラスタごとの `Range.getBoundingClientRect()` を DOM 順にたどり、inline 座標が戻って block 座標が進んだところで行を割る |
| **はみ出し** | `max(inline_start + inline_size) − rect[2]`（`overflows` フィールドは無いので計算する）。**祖先の箱との共通部分**で測る（flex アイテムは自分の箱が親より広くなる） | 断片の inline の終端が包含ブロックを超えた量 |
| **欠落** | 断片の ink（横書きは hhea の ascent / descent、縦書きは中心軸の前後 `font-size/2`）が、ブロックの箱や紙面の外へ出た量 | クラスタの `Range` の箱が同じように外へ出た量 |
| **重なり** | 同じ行の隣り合うクラスタの箱が inline 方向に重なる量と、**クラスタごとの字送り**（グリフの inline 位置の差） | 同じ |

**比べないもの**:

- **グリフ単位の x**。shashoku はグリフ原点をデバイスピクセルに丸める（A8）ので、
  サブピクセル配置の Chrome とは必ず 1px 未満の系統差が出る
- **block 方向の絶対座標**。`line-height: normal` の作り方が違う（下の §3-1）
- **ピクセルの色**。アンチエイリアスとガンマは別物

**許容差**: inline 方向 1.0 px、block 方向 2.5 px（`compare.py` の `TOL_INLINE` / `TOL_BLOCK`）。
Chrome の LayoutUnit は 1/64 px、shashoku は FreeType の 26.6 なので、0.02 px 程度の差は常に出る。

## 2. 差の分類

出た差は次の 4 つに仕分ける。**`差` と出ただけでは「shashoku の誤り」ではない。**

1. **意図した差** — shashoku が仕様としてそう決めているもの。**必ず ARCHITECTURE.md の A 番号を添える**
   （添えられないものは判断記録が無いということなので、書き足す）
2. **shashoku の誤り** — 個別の issue にする
3. **Chrome の方が日本語組版として劣る** — 直さない。ここに入れた理由を書く
4. **未対応による差** — 機能が入っていないだけで、いまの振る舞いが正しいと決めたわけではないもの。
   README の「既知の制限」を指す。**「意図した差」と混ぜない**（混ぜると、入れるべき機能が
   「決めたこと」として固まってしまう）

判定の印は `OK`（差なし）/ `差` / `??`（比較不能）/ `期待`（拒否されるのが正しい入力）/ `失敗`。

## 3. 比較の土台をそろえるためにしていること

### 3-1. フォント

shashoku に渡すのと**同じファイル**を `@font-face` で読ませる（`build/_assets/fonts/`）。
family 名は `SHK0` / `SHK1` … に付け替える。同名のシステムフォントを拾わないため。
shashoku は「フォントファイルの family 名でまとめ、その中で weight が近いものを選ぶ」
（§3.5）ので、同じ family のファイルは同じ `SHK<n>` にまとめて `font-weight` だけ変える。

**本当にそのフォントで描かれたかの確認**は 2 段構えにしてある。`document.fonts` の
`status` だけでは「ある文字だけシステムフォントに落ちた」を見逃すので、同じ文字列の幅を
shashoku と突き合わせる（欧文は字幅がフォントごとに大きく違うので効く）。結果は
`report.txt` の冒頭に出る。

### 3-2. 既定のスタイル

`src/style/ua_stylesheet.cpp` と同じ規則を Chrome 側にも入れる（`h1`〜`h6` と `p` のマージン、
`rt { font-size: 0.5em }`）。加えて:

- `line-break: strict` — CLI の既定が `--line-break strict`
- `font-synthesis: none` — shashoku は合成ボールドを作らない
- `margin: 0` — shashoku の `#root` にマージンは無い

### 3-3. 紙面の大きさ

WSL から Windows の `chrome.exe` を呼ぶと `--window-size` が当てにならない
（幅は 500 px 未満にならず、`--dump-dom` のときは `window.innerWidth` が 0 になる）。
そこで紙面は CSS で決めている: `#shk-root` を `position: absolute; left: 0; top: 0` で
物理的な左上に固定し、幅（縦書きは高さも）を指定する。スクリーンショットは 1:1 の CSS px で
撮れるので、大きめのウィンドウで撮ってから左上を切り出せば、shashoku の PNG と同じ範囲になる。

Chrome の方が背が高くなるケース（行高の丸めの違いや、折り返しが増えたとき）では、
Chrome 自身のルートが入る高さまで切り出す。並べた画像の高さが違うのはそのため。

### 3-4. 縦書き

shashoku は `writing-mode` を文書全体で 1 つしか持たない（A1）ので、Chrome 側でも
`html` に `writing-mode: vertical-rl` を置く。断片の `div` だけを縦にすると紙面の向きが食い違う。

測定値は **Chrome 側を論理座標に直してから**比べる（縦書きは inline = y、block = −x）。
#15 の本文は「縦書きは `display-list` を使うのが楽」としているが、Chrome 側を論理に直せば
横書きと同じ 1 本のコードで比べられるので、`box` に一本化した。

### 4-1. 直った 4 件（この 4 つの判定で見つかり、修正で消えた）

- **#16**（ケース 1・2）— ルビの親文字に `letter-spacing` が入らなかった。
  修正後、ケース 1 の親文字の字送りは shashoku 35.47 / Chrome 35.45 px（差 0.02 px）で、
  直後の通常テキスト（48.00 px）とも辻褄が合う。**ケース 1 は 4 つとも OK になった**
- **#17**（ケース 3）— 親文字の中の大きい `<span>` が行の高さに数えられなかった。
  修正後、行の箱からはみ出す ink は 0.0 px（修正前は 62.7 px）。絵でも、
  80 px の `B` が画像の中に収まっている
- **#18**（ケース 8）— `overflow-wrap: anywhere` が flex アイテムの min-content に効かなかった。
  修正後は Chrome と同じ 3 行（`ABC` / `DEF` / `GH`）に折り返し、はみ出しも 0.0 px
- **#19**（ケース 20）— 計算値が非有限になっても成功していた。修正後は
  `error[limit-exceeded] at 3:6: padding-top computes to inf (1e+38em x font-size 16 px) …` で
  **位置つきのエラー終了**。比較スクリプトはこれを「入力を拒否した（期待どおり）」と報告する
  （`cases.json` の `expect_error`）。**Chrome は同じ入力を 2^25 = 33554432 px で飽和させ、
  `有` / `限` の 2 行に折り返して描く。** どちらも「黙って壊れた絵を出す」ことはしない

### 4-2. 未対応による差（機能が入っていないだけで、いまの形が正しいと決めたわけではない）

**ルビの 1:2:1 の配分とルビの掛け**（README の「既知の制限」/ ARCHITECTURE.md A41）。
ルビのあるケース 2・3・4・5・7・21・23 の「重なり」の差はすべてこれ。Chrome は
CSS Ruby の既定（`ruby-align: space-around`）で **短い方を長い方の幅まで均等に広げ**、
さらに **組を隣の文字に数 px 掛ける**。shashoku はどちらもせず、短い方を中央に置くだけ。

| 実測 | shashoku | Chrome |
|---|---|---|
| ケース 5 `<ruby>写植<rt>しゃしょく</rt></ruby>` の親文字の字送り | 16.00 px（そのまま） | 20.00 px（注記の 40 px に合わせて配分） |
| 同 親文字の箱 / 組の箱 | `[4, 36]` / `[0, 40]`（中央に置く） | `[0, 40]` / `[0, 40]`（広げる） |
| ケース 3 `<rt>ab</rt>` の注記の字送り | 4.50 px（そのまま） | 30.92 px（親文字の 62.3 px に合わせて配分） |
| ケース 4 で組が隣の文字に掛かる量 | 0 px | 2 px（前の `は` の送りが 16 → 14 px になる） |

「掛け」が無いまま親文字の側だけ広げても JLREQ には近づかない（広げたぶんが行全体を
間延びさせる）ので、**1:2:1 と掛けはまとめて入れる**。

### 4-3. 意図した差（A 番号つき）

- **`<rt>` に `letter-spacing` を適用しない** — **A37**。和文のルビは親文字に対する配分で
  決まる（JLREQ 3.3）ので、親文字の字間がルビ文字の間にも入るとルビが親文字より広がって
  別の語のように見える。Chrome は継承した字間を `<rt>` にも掛けるので、字間つきのルビの
  ケースで差が残る。実測（ケース 2、`font-size:32px; letter-spacing:16px`）:
  注記 `とうきょう` の字送りが shashoku 16.00 px / Chrome 32.00 px。
  **この差はルビ組の幅を変えるので、親文字の側にも波及する**: 組の幅が
  shashoku 96 px（親文字の送り）/ Chrome 160 px（広がった注記）になり、Chrome は
  そこに合わせて親文字も広げるため、親文字の字送りが 48.00 / 80.00 px になる。
  ケース 2・21 の「親文字の差」はこれが原因で、#16 の直し残しではない
  （ケース 2 の 48.00 px = `font-size 32 + letter-spacing 16` で、shashoku 側は正しい）
- **ルビを「親文字の送り」の中央に置く** — **A37**。末尾の字間を含む送りの中央なので、
  字間があるとルビの中心は親文字の**インク**の中心より字間の半分だけ後ろに来る。
  **Chrome も同じだった**。実測（ケース 1、`<ruby>ABC<rt>x</rt></ruby>`、32 px・字間 16 px）:
  親文字の送りは両者とも `[0, 108.906]`（末尾の字間 16 px を含む）、注記の中心も両者 54.45 px。
  インクの中心（`C` の開始 72.48 + そのグリフの送り ≒ 92.9 の中点 ≒ 46.4 px）ではない。
  **「送りの中央か、インクの中央か」は両エンジンとも送りの中央**
- **`<img>` を stretch で歪めない** — **A18**。交差軸のサイズを auto にした `<img>` を
  `align-items: stretch` の flex アイテムに置くと、Chrome はアイテムの箱を行の高さまで
  伸ばす（実測 64×72）。shashoku は固有寸法のまま（64×64）。4 つの数値の判定には出ない
- **`text-align: justify` と約物のアキ詰めの組み合わせ** — **A13 × A16**。shashoku は
  詰めた箇所を配分から外し、残りに広く配る（26.00 / 29.20 px）。Chrome は約物の前後も
  含めて均等に配る（28.00 px）。行の幅はどちらも 240 px ぴったりで、改行位置も同じ
- **縦書きの `<img>` の中央揃え** — #15 本文の候補 8。判定には出ない
- **全角文字どうしの間の改行を消す** — **A14**。`examples/` の 3 つ（22・23・24）の
  改行位置の差はこれ。ソースの HTML で全角文字の間に改行があると、shashoku はその改行を
  消し、Chrome は空白 1 個として残す。実測（`examples/hello.html`）:
  shashoku `…エンジンです。行頭に「。」や…` / Chrome `…エンジンです。 行頭に「。」や…`。
  行に入る文字数が 1 字ずれるので、クラスタ数も合わなくなり重なりは比較不能になる

「Chrome の方が日本語組版として劣る」に分類したものは、修正前も修正後もなかった。

### 4-4. 一致していて、むしろ安心できたもの

- **改行位置**: ケース 8（#18。修正後は一致）と A14 の影響を受ける `examples/` の 3 つ以外の
  **すべてで文字列が完全に一致**した。禁則（ケース 4。字送りだけなら 13 字目の `、` が
  行頭に来るところを、両者とも 12 字目の `ら` を次の行へ送った）、flex の中の折り返し
  （6・9・17）、`<br>`（7）、縦書き（15・16・17）、`examples/og_card.html`（25。6 行すべて）を含む
- **約物のアキ詰め**（ケース 13）: `」` と `。` が続く箇所の字送りが、両者とも 26 → **16 px**。
  行末の `。` の詰めも 25.41 / 25.39 px でほぼ一致。A16（JLREQ 3.1.4）は Chrome の
  `text-spacing-trim` の既定と同じ結果になっている
- **`examples/og_card.html`**（ケース 25）: 1200×630 の flex・画像・背景・角丸・和欧混植・
  `font-weight: 700` を全部使った入力で、4 つの判定がすべて OK。絵も並べて見分けがつかない
- **フォント**: `Hamburgefonstiv` の幅が shashoku 161.453 / Chrome 161.422（差 0.03 px）。
  Chrome 側も同じ Noto Sans JP で描いている
- **和欧混植のフォールバック**（ケース 19）: `letter-spacing` が和文側に二重に入ることはない

### 4-5. 比較の仕組みの側で分かったこと

- **`<rt>` の字送りは親文字と分けて数える。** 混ぜると「#16 が直ったこと」と
  「A37 の意図した差」が同じ 1 つの数字に潰れる
- **Chrome の `<rt>` の `Range` が返すのは「割り当てられた枡」で、グリフの送りではない。**
  1 文字の注記の箱が親文字の送りいっぱい（実測 108.91 px）に広がるので、注記の側は
  **クラスタ間の送りだけ**を比べる（最後のクラスタ = 箱の幅は落とす）
- **ルビ組の切り出しは座標から推測しない。** Chrome は DOM の `<ruby>` から、shashoku は
  box ダンプの断片の並び（注記の直前から後ろ向きに伸ばし、親文字の送りの中心が注記の中心と
  一致したところで止める）から取る
- **Chrome の `line-height: normal` は shashoku より 0.8 px 高い**（16 px の行で 24.0 と
  23.171875）。Chrome が ascent / descent を整数 px に丸めるため。block 方向の絶対座標を
  比べてはいけない理由がこれ
- **合字があるとクラスタ単位で比べられない**。Noto Sans JP には `fl` の合字があり、
  `flex` という単語を含めるとグリフ数とクラスタ数が合わなくなる。比較ケースの欧文は
  合字にならない綴りにしてある。`examples/vertical.html` の `——` も 1 グリフに合成される
- **Chrome は `<rt>` のインラインボックスを親ブロックの箱から 4 px はみ出させる**。
  ルビの帯の作りが違うだけで欠落ではないので、判定からは外してある
- **WSL から呼ぶ `chrome.exe` は `--window-size` が当てにならない**。幅は 500 px 未満にならず、
  `--dump-dom` のときは `window.innerWidth` が 0 になる。小さすぎるウィンドウでは内容が
  描かれないことがある（実測: 300x117 ではルビの親文字が出ず、600x300 では出る）。
  紙面は CSS で決め、スクリーンショットは大きめに撮ってから切り出している

### 4-6. この先やるとよいこと

- **`--dump-stage display-list` との突き合わせ**: いまは `box` だけを見ているので、
  背景・枠線・角丸の箱（`fill_rect` / `stroke_rounded_rect`）と Chrome の
  `getBoundingClientRect()` は比べていない。ケース 10 のように「4 つの判定には出ないが
  箱の大きさが違う」差はここで拾える
- **1:2:1 の配分とルビの掛けを入れたら、ケース 2・3・4・5・7・21 を測り直す。**
  4-2 の表の数値がそのまま受け入れ条件になる
- **ケースを足す**: いまの 1〜21 は #15 のコメントの一覧そのまま。**直した issue の再現入力は
  ケースとして残す**（直ったことが次から自動で見える。今回の 4 件がその実例）
- **CI には入れない**（#15 の方針）。Chrome のバージョンが変わると値が変わるので、
  「差が出たら失敗」にはしない。差の表を人が読むための道具として使う
